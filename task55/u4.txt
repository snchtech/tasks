Функціонал звіту працює як керований Interactive Report, де користувач задає два основні параметри: **дату формування** і **unit**. Після цього SQL автоматично визначає потрібні часові зрізи, відбирає відповідні записи з `ARM_OUTFIT_TREE_COUNTER_V`, агрегує виконавців по `performer_department_id` і формує готову табличну структуру для перегляду та експорту в Excel.

Схематично логіка для користувача така:

```text
Користувач вибирає:

Дата формування: 16.08.2026
Unit: Тест 1

            ↓

Система визначає часові зрізи:

Наряди:
15.08.2026 13:00
15.08.2026 21:00
16.08.2026 06:00

Розпорядження:
15.08.2026 13:00
15.08.2026 21:00
16.08.2026 06:00

            ↓

З ARM_OUTFIT_TREE_COUNTER_V
відбираються записи відповідно до:
- вибраної дати;
- вибраного unit;
- вибраних підрозділів, якщо застосовано фільтр.

            ↓

Дані агрегуються по performer_department_id

            ↓

Формується Interactive Report
```

Для `unit` логіка така. Значення `P11_UNIT` визначає, яку саме числову колонку брати з view:

```text
P11_UNIT = 1
→ використовується U1_PEOPLE
→ заголовок звіту "Тест 1"

P11_UNIT = 2
→ використовується U2_PEOPLE
→ заголовок звіту "Тест 2"

P11_UNIT = 0
→ використовується U3_PEOPLE
→ заголовок звіту "Тест 3"
```

Тобто SQL не змінюється залежно від unit. Змінюється лише джерело числового показника:

```sql
CASE :P11_UNIT
    WHEN '1' THEN u1_people
    WHEN '2' THEN u2_people
    WHEN '0' THEN u3_people
END
```

Це важливо, тому що один Interactive Report можна використовувати для всіх трьох варіантів.

Щодо дати: користувач вибирає не шість окремих дат і часів, а лише **дату формування звіту**. На її основі автоматично визначаються три контрольні моменти. Наприклад, якщо вибрано `16.08.2026`, система формує:

```text
13:00 → 15.08.2026 13:00
21:00 → 15.08.2026 21:00
06:00 → 16.08.2026 06:00
```

Тобто перші два зрізи належать попередній добі, а третій — поточній.

Для кожного такого моменту перевіряється, чи запис був активним:

```text
status_start_date <= момент зрізу

і

status_end_date IS NULL
або
status_end_date >= момент зрізу
```

Наприклад, якщо наряд почав діяти 15.08 о 10:00 і завершився 16.08 о 08:00, він потрапить у всі три зрізи:

```text
13:00 → так
21:00 → так
06:00 → так
```

Якщо завершився 15.08 о 18:00:

```text
13:00 → так
21:00 → ні
06:00 → ні
```

Після відбору дані не виводяться безпосередньо з `department`. Основною ознакою рядка звіту є саме **підрозділ-виконавець — `performer_department_id`**.

Наприклад, у базі є:

```text
department A
performer_department_id = 101
кількість = 3

department B
performer_department_id = 101
кількість = 5

department C
performer_department_id = 101
кількість = 2
```

У звіті користувач не побачить три окремі записи. Вони будуть об'єднані:

```text
Підрозділ 101 | 10
```

Тобто система відповідає на питання: **скільки працівників конкретного підрозділу-виконавця зараз задіяно незалежно від того, у яких вихідних підрозділах вони працюють**.

`nr` розділяє два типи робіт:

```text
nr = 1 → Наряди
nr = 2 → Розпорядження
```

Тому для кожного виконавця формується шість числових показників:

```text
                      НАРЯДИ                      РОЗПОРЯДЖЕННЯ

                 13:00   21:00   06:00       13:00   21:00   06:00
```

Плюс окрема колонка `Примітка` для кожної групи.

У результаті користувач бачить приблизно таку структуру:

```text
                НАРЯДИ                         РОЗПОРЯДЖЕННЯ
Підрозділ    13:00  21:00  06:00  Прим.    13:00  21:00  06:00  Прим.

Підрозділ 1    12     10      8                3      2      1
Підрозділ 2     7      6      5                1      1      0
Підрозділ 3     4      5      3                2      1      1
...
Підрядник 1     3      2      2                1      0      0
Підрядник 2     5      4      3                0      1      0

----------------------------------------------------------------

Всього          31     27     21                7      5      2

Кількість
працюючих       38     32     23
```

Рядок **`Всього`** підсумовує кожну з шести числових колонок окремо. Тобто для нарядів окремо рахується 13:00, 21:00 і 06:00, і так само окремо для розпоряджень.

Рядок **`Кількість працюючих`** має іншу логіку. Він заповнюється тільки у перших трьох часових колонках:

```text
13:00 =
Всього Наряди 13:00
+
Всього Розпорядження 13:00

21:00 =
Всього Наряди 21:00
+
Всього Розпорядження 21:00

06:00 =
Всього Наряди 06:00
+
Всього Розпорядження 06:00
```

Тобто якщо:

```text
Наряди 13:00 = 31
Розпорядження 13:00 = 7
```

користувач побачить:

```text
Кількість працюючих 13:00 = 38
```

У другій групі колонок для цього рядка значення залишаються порожніми.

При зміні `P11_UNIT` або дати звіт має оновлюватися через Dynamic Action. Загальна схема така:

```text
Користувач змінює P11_UNIT
        або
Користувач змінює P11_REPORT_DATE

            ↓

Dynamic Action

            ↓

Items to Submit:
P11_UNIT
P11_REPORT_DATE
P11_MODAL_DEPARTMENTS

            ↓

Refresh Interactive Report

            ↓

SQL виконується повторно

            ↓

Формується новий набір даних
```

Для `P11_UNIT` додатково змінюється заголовок. Наприклад:

```text
Unit = 1 → Тест 1
Unit = 2 → Тест 2
Unit = 0 → Тест 3
```

Тому при зміні unit бажаний порядок Dynamic Action:

```text
Change P11_UNIT
      ↓
Execute Server-side Code
      ↓
оновити P11_REPORT_TITLE
      ↓
Refresh region / title
      ↓
Refresh Interactive Report
```

Для зміни дати достатньо:

```text
Change P11_REPORT_DATE
      ↓
Refresh Interactive Report
```

Якщо використовується також фільтр підрозділів:

```text
Change P11_MODAL_DEPARTMENTS
      ↓
Refresh Interactive Report
```

При цьому фільтр `department` визначає, **з яких вихідних підрозділів брати дані**, а фінальна агрегація все одно виконується по `performer_department_id`.

Наприклад:

```text
Вибрано department A і B

department A → performer 101 → 3
department B → performer 101 → 5
department C → performer 101 → 7
```

Оскільки `department C` не вибраний, результат буде:

```text
Підрозділ 101 → 8
```

а не `15`.

Для оформлення ти правильно плануєш використовувати стандартний **Highlight Interactive Report**. Для цього SQL повертає службове поле:

```text
DETAIL
TOTAL
WORKERS_TOTAL
```

За ним можна створити правила Highlight:

```text
DETAIL
→ світло-бежеве оформлення клітинки "Підрозділи"

TOTAL
→ окреме оформлення рядка "Всього"

WORKERS_TOTAL
→ окреме оформлення "Кількість працюючих"
```

Перевага тут у тому, що це не просто CSS поверх HTML, а штатний механізм IR, тому оформлення краще узгоджується з експортом.

Щодо Excel: структура звіту вже спеціально під це підготовлена. В Interactive Report задаються дві групи колонок:

```text
НАРЯДИ
    13:00
    21:00
    06:00
    Примітка

РОЗПОРЯДЖЕННЯ
    13:00
    21:00
    06:00
    Примітка
```

Тому в APEX на екрані користувач працює зі звичайним Interactive Report, може застосовувати його стандартні можливості, а при експорті отримує зрозумілу структуру Excel із групами колонок.

У підсумку сценарій роботи користувача максимально простий:

```text
1. Вибрати дату.

2. Вибрати Unit:
   Тест 1 / Тест 2 / Тест 3.

3. За потреби вибрати підрозділи.

4. Звіт автоматично оновлюється.

5. Користувач бачить:
   - підрозділи-виконавці;
   - 3 зрізи по нарядах;
   - 3 зрізи по розпорядженнях;
   - два блоки приміток;
   - Всього;
   - Кількість працюючих.

6. За потреби натискає стандартний Download / Excel
   в Interactive Report.

7. В Excel отримує той самий набір даних,
   згрупований на "Наряди" і "Розпорядження".
```

Це якраз той варіант, де **користувач керує тільки параметрами, а всю складну логіку часових зрізів, unit, агрегації та підсумків бере на себе SQL**.
