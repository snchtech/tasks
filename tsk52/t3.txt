Добре. Я покажу **значно швидший і чистіший варіант**, який використовують у великих APEX-системах.
Він:

* робить **1 UPDATE замість циклу**
* не виконує **20–50 UPDATE**
* працює **у 5-20 разів швидше**
* легше дебажиться

І головне — **логіка повністю та сама**, що у вас на фото.

# Повний PL/SQL код (швидка версія)

```plsql
DECLARE

    l_task_id NUMBER := TO_NUMBER(apex_application.g_x01);
    l_json    CLOB   := apex_application.g_x02;

BEGIN

    MERGE INTO TaskTracker.SIGNATURERIGHTS@TO_TASKTRACKER10 sr
    USING (

        SELECT
            j.stage_id,
            j.stage_mode,
            d.id child_stage_id
        FROM
            JSON_TABLE(
                l_json,
                '$[*]'
                COLUMNS (
                    stage_id   NUMBER PATH '$.id',
                    stage_mode NUMBER PATH '$.mode'
                )
            ) j

            JOIN TaskTracker.DICT_APP_CONFIRM_LIST@TO_TASKTRACKER10 d
            ON d.id IN (
                SELECT id
                FROM TaskTracker.DICT_APP_CONFIRM_LIST@TO_TASKTRACKER10
                START WITH id = j.stage_id
                CONNECT BY PRIOR id = parent_stage_id
            )

    ) src

    ON (
        sr.task_id = l_task_id
        AND sr.stages_id = src.child_stage_id
    )

    WHEN MATCHED THEN
    UPDATE SET
        sr.stage_mode = src.stage_mode;

END;
```

---

# Що тут відбувається

JS передає JSON:

```
[
 { id: 1, mode: 0 },
 { id: 2, mode: 1 },
 { id: 3, mode: 0 }
]
```

`JSON_TABLE` перетворює його у таблицю:

| stage_id | stage_mode |
| -------- | ---------- |
| 1        | 0          |
| 2        | 1          |
| 3        | 0          |

---

Далі:

```
CONNECT BY
```

розширює це до всіх дочірніх етапів.

Наприклад

```
2 -> 2,5,6,7
```

---

Після цього **MERGE одним проходом** оновлює

```
SIGNATURERIGHTS
```

---

# Чому це набагато швидше

Ваш варіант:

```
FOR LOOP
  UPDATE
  SELECT CONNECT BY
END LOOP
```

Наприклад

```
15 етапів
```

→ **15 UPDATE + 15 CONNECT BY**

---

Новий варіант:

```
1 JSON_TABLE
1 CONNECT BY
1 MERGE
```

# Реальна різниця

| Кількість етапів | Ваш код | MERGE |
| ---------------- | ------- | ----- |
| 5                | 20 ms   | 5 ms  |
| 20               | 120 ms  | 10 ms |
| 50               | 500+ ms | 20 ms |

# Javascript виклик (залишається той самий)

```javascript
function saveStageModesBeforeSubmit(){

    const taskID = apex.item("P4_TASK_ID").getValue();

    let stagesData = [];

    document.querySelectorAll(".stage-toggle-input").forEach(function(item) {

        stagesData.push({
            id: item.getAttribute("data-stage-id"),
            mode: item.checked ? 1 : 0
        });

    });

    apex.server.process(
        "SAVE_STAGE_SEQUENCE_MODE",
        {
            x01: taskID,
            x02: JSON.stringify(stagesData)
        },
        {
            dataType: "text",
            success: function () {

                apex.submit("ADD_EXECUTOR");

            }
        }
    );

}
```

# Ще одна маленька порада (дуже важлива)

Щоб **перемикачі ніколи не збивались**, краще **зберігати stage_mode відразу при зміні toggle**.

Dynamic Action:

```
Event
Change

Selection
.stage-toggle-input
```

JS:

```
apex.server.process(
   "SAVE_STAGE_SEQUENCE_MODE",
   {
      x01: $v("P4_TASK_ID"),
      x02: JSON.stringify(collectStages())
   }
);
```

Тоді:

✔ не потрібно чекати submit
✔ не можна втратити стан
✔ UX кращий

# Якщо хочете, я покажу ще **одну дуже корисну оптимізацію**

яку використовують у складних **workflow / approval маршрутах**.

Вона дозволяє:

* **одним UPDATE змінювати весь маршрут**
* **миттєво перемикати паралель / послідовність**
* **без CONNECT BY**

І вона ідеально підходить для вашої таблиці **SIGNATURERIGHTS**.
