Так, тут краще **розділити два різні процеси**:

1. **відмітка виконання** → це `SIGNATUREHISTORY`
2. **звичайні коментарі виконавця/по виконавцю** → окрема таблиця коментарів

Це найбільш чистий і масштабований підхід.
Тоді `SIGNATUREHISTORY.NOTE` не треба використовувати для всіх коментарів підряд. Його краще залишити тільки для випадку:

* користувач натиснув кнопку відмітки
* при цьому ввів коментар саме до цієї відмітки

Тобто `NOTE` = **коментар до факту зміни статусу**, а не загальний чат/журнал коментарів.

# 1. Що я раджу по структурі

## Основна ідея

Коментарі треба прив’язати **до конкретного запису виконавця** з `SIGNATURERIGHTS.ID`.

Це правильно, бо саме `SIGNATURERIGHTS` у тебе фактично описує:

* хто виконавець
* по якому завданню
* по якому підзавданню
* по якому етапу
* в якому контексті

Тому окрема таблиця зв’язку типу many-to-many тут, швидше за все, **не потрібна**.

Бо логіка така:

* **один запис `SIGNATURERIGHTS`**
* має
* **багато коментарів**

Це класичний зв’язок **1:N**.

# 3. Які поля ще варто додати

Окрім тих, що ти запропонував, я дуже раджу такі:

### обов’язково корисні

* `SIGNRIGHT_ID` — прив’язка до виконавця
* `DATE_UPDATE` — коли коментар редагували
* `UPDATOR_ID` — хто редагував
* `IS_DELETED` — м’яке видалення
* `DATE_DELETE`
* `DELETOR_ID`

### опціонально

* `COMMENT_TYPE` — якщо потім захочеш типи коментарів (`INFO`, `WARNING`, `SYSTEM`)
* `PARENT_COMMENT_ID` — якщо захочеш відповіді на коментарі
* `SOURCE_TYPE` — якщо коментар створився з форми, API, автоматично
* `DISPLAY_ORDER` — зазвичай не треба, бо є `DATE_CREATE`

Але для твоєї задачі зараз достатньо:

```sql
ID
SIGNRIGHT_ID
DATE_CREATE
CREATOR_ID
COMMENT_TEXT
DATE_UPDATE
UPDATOR_ID
IS_DELETED
```

# 4. Чи потрібна таблиця зв’язку між `EXECUTOR_COMMENTS` та `SIGNATURERIGHTS`

**Ні, не потрібна**, якщо один коментар належить тільки одному виконавцю.

Таблиця зв’язку потрібна, якщо:

* один коментар може належати одразу кільком виконавцям
* або один шаблон коментаря розкидається на багато виконавців

У тебе ж бізнес-логіка інша:
коментар пишеться **в контексті конкретного рядка виконавця**.

Тому достатньо:

```sql
EXECUTOR_COMMENTS.SIGNRIGHT_ID -> SIGNATURERIGHTS.ID
```

# 5. Що робити з полем `NOTE` у `SIGNATUREHISTORY`

Я б залишив таку логіку:

## `SIGNATUREHISTORY.NOTE`

використовується **лише коли коментар є частиною відмітки**.

Наприклад:

* "виконано із зауваженням"
* "передано черговому"
* "затримка через ..."

Тобто це коментар, який належить саме до запису історії статусу.

## `EXECUTOR_COMMENTS.COMMENT_TEXT`

це окремий вільний коментар, який можна додати без натискання кнопки відмітки.

# 10. Функція для пакета `get_executor_comments(sign_id)`

Тут є важливий момент:
якщо ти хочеш повертати **готовий текст/HTML для картки**, то функція може повертати `CLOB`.

Це найзручніше для APEX dynamic content.

---

## Приклад функції, що повертає HTML

```sql
create or replace package task_pkg as
    function get_executor_comments(p_signright_id number) return clob;
end task_pkg;
/
```

```sql
create or replace package body task_pkg as

    function get_executor_comments(p_signright_id number) return clob is
        l_result   clob;
    begin
        l_result := empty_clob();

        for r in (
            select
                row_number() over(order by ec.date_create) as rn,
                ec.comment_text,
                ec.date_create,
                ec.creator_id
                -- тут за потреби приєднуй таблицю users
                -- u.full_name as creator_name
            from executor_comments ec
            where ec.signright_id = p_signright_id
              and nvl(ec.is_deleted, 0) = 0
            order by ec.date_create
        ) loop
            l_result := l_result ||
                '<div class="executor-comment-item">' ||
                    '<div class="executor-comment-head">' ||
                        '<span class="executor-comment-num">' || r.rn || '.</span> ' ||
                        '<span class="executor-comment-date">' || to_char(r.date_create, 'dd.mm.yyyy hh24:mi') || '</span>' ||
                    '</div>' ||
                    '<div class="executor-comment-text">' ||
                        apex_escape.html(
                            case
                                when length(r.comment_text) > 4000 then substr(r.comment_text, 1, 4000) || '...'
                                else r.comment_text
                            end
                        ) ||
                    '</div>' ||
                '</div>';
        end loop;

        if l_result is null or dbms_lob.getlength(l_result) = 0 then
            l_result := '<div class="executor-comment-empty">Коментарі відсутні</div>';
        end if;

        return l_result;
    end get_executor_comments;

end task_pkg;
/
```

# 11. Але тут є нюанс по 4000 символів

Ти написав:

> важливо використати обмеження тексту 4000, і далі просто показувати ...

Якщо поле `COMMENT_TEXT` вже `VARCHAR2(4000 CHAR)`, то **більше 4000 там фізично не збережеться**.
Тобто логіка обрізання фактично не потрібна.

### Тому є 2 варіанти:

## Варіант А — лишити `VARCHAR2(4000)`

Тоді в UI просто показувати весь текст.
`...` не знадобиться.

## Варіант Б — зробити `CLOB`

Якщо теоретично коментарі можуть бути довгі, тоді:

* у БД `COMMENT_TEXT CLOB`
* а в картці показуєш `dbms_lob.substr(..., 4000, 1) || '...'`

Для твоєї задачі я б поки лишив:

```sql
COMMENT_TEXT varchar2(4000 char)
```

# 13. Функція вставки коментаря

Я б не робив прямий insert по сторінках у багатьох місцях.
Краще через пакет.

## Специфікація

```sql
create or replace package task_pkg as
    procedure add_executor_comment(
        p_signright_id in number,
        p_comment_text in varchar2,
        p_creator_id   in number
    );

    function get_executor_comments(p_signright_id number) return clob;
end task_pkg;
/
```

## Body

```sql
create or replace package body task_pkg as

    procedure add_executor_comment(
        p_signright_id in number,
        p_comment_text in varchar2,
        p_creator_id   in number
    ) is
    begin
        if p_signright_id is null then
            raise_application_error(-20001, 'Не вказано SIGNRIGHT_ID');
        end if;

        if trim(p_comment_text) is null then
            raise_application_error(-20002, 'Коментар не може бути порожнім');
        end if;

        insert into executor_comments (
            signright_id,
            comment_text,
            date_create,
            creator_id,
            is_deleted
        ) values (
            p_signright_id,
            trim(p_comment_text),
            sysdate,
            p_creator_id,
            0
        );
    end add_executor_comment;


    function get_executor_comments(p_signright_id number) return clob is
        l_result clob;
    begin
        l_result := empty_clob();

        for r in (
            select
                row_number() over(order by ec.date_create) as rn,
                ec.comment_text,
                ec.date_create
            from executor_comments ec
            where ec.signright_id = p_signright_id
              and nvl(ec.is_deleted, 0) = 0
            order by ec.date_create
        ) loop
            l_result := l_result ||
                '<div class="executor-comment-item">' ||
                '<b>' || r.rn || '.</b> ' ||
                '<span>' || to_char(r.date_create, 'dd.mm.yyyy hh24:mi') || '</span><br>' ||
                '<span>' || apex_escape.html(r.comment_text) || '</span>' ||
                '</div>';
        end loop;

        if l_result is null or dbms_lob.getlength(l_result) = 0 then
            l_result := 'Коментарі відсутні';
        end if;

        return l_result;
    end get_executor_comments;

end task_pkg;
/
```

# 14. Якщо потрібні імена авторів

Тоді в коментарях краще одразу зберігати `CREATOR_ID`, а ім’я підтягувати через join.

Наприклад:

```sql
select
    row_number() over(order by ec.date_create) as rn,
    ec.comment_text,
    ec.date_create,
    u.full_name
from executor_comments ec
left join app_users u on u.id = ec.creator_id
where ec.signright_id = :P_SIGNRIGHT_ID
  and nvl(ec.is_deleted, 0) = 0
order by ec.date_create;
```

# 17. Що ще можна доробити

Я б одразу передбачив:

### 1. Редагування тільки власних коментарів

У картці виконавця:

* останній коментар
* кнопка “ще”

### 5. Розмежування прав

Хто може:

* бачити коментарі
* додавати коментарі
* редагувати свої
